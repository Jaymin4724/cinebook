# CineBook Load Testing (Locust)

This directory contains Locust-based load tests for CineBook's critical paths:

* **Seat Booking** (`lock → book`)
* **Rate Limiter**
* **Whole Application Latency**

The tests run directly against a locally running FastAPI application. Docker Compose is **not** required. PostgreSQL, Redis, and Elasticsearch are expected to already be running (for example, in Docker containers with their ports exposed to the host).

## Directory Structure

```text
loadtest/
├── seed_loadtest_data.py      # Seeds a fresh show and test users
├── locustfile.py              # FullAppUser, SeatBookingUser, RateLimitUser
├── loadtest_data.json         # Generated by the seeder (do not commit)
├── reports/                   # HTML and CSV reports
└── README.md
```

---

# How It Works

1. The seeder inserts a fresh theatre, layout, screen, movie, show, and a pool of users into the database configured by `TEST_DB_URL`.
2. It generates `loadtest_data.json` containing:

   * Show ID
   * Seat IDs
   * User IDs
3. `locustfile.py` reads this file and generates JWT access tokens using the application's own helper:

```python
helper.generate_access_token_and_refresh_token(...)
```

No OTP or email verification is required, and tokens are always freshly generated.

4. Seat booking is tested using the real booking flow:

```text
POST /seat-lock
        ↓
POST /seat-book
```

Expected race-condition responses (`400`, `403`, `409`) are treated as **successful outcomes**, since they indicate that locking is working correctly.

Only the following count as failures:

* 5xx responses
* Authentication failures
* Invalid or malformed responses

# 1. Run the Application Against the Test Database

The seeder writes data into `TEST_DB_URL`, while the application reads from `DB_URL`.

Point the application to the same database.

### PowerShell

```powershell
$env:DB_URL = $env:TEST_DB_URL
```

### Bash

```bash
export DB_URL="$TEST_DB_URL"
```

This keeps load-test data separate from your normal development database.

If you intentionally want to test against your development database instead, seed using:

```bash
TEST_DB_URL=<your DB_URL> uv run python loadtest/seed_loadtest_data.py
```

| `LOADTEST_USERS` | 50      | Number of users created |
| `LOADTEST_ROWS`  | 20      | Seat rows               |

* 20 × 30
* 600 seats

## Rate Limiter Test

Run the application with:

```text
ENV=PRODUCTION
```

Then execute:

```bash
uv run locust \
    -f loadtest/locustfile.py \
    --host http://localhost:8000 \
    --headless \
    --users 20 \
    --spawn-rate 20 \
    --run-time 30s \
    RateLimitUser
```

At the end of the run a summary similar to the following is printed:

```text
Rate-limit summary

Allowed requests : XX
429 responses    : XXXX
```

With the default bucket configuration (capacity = 10), expect a small burst of successful requests followed by mostly `429 Too Many Requests`.

## Whole Application Latency Test

Run the application with:

```text
ENV=TESTING
```

to disable rate limiting.

```bash
uv run locust \
    -f loadtest/locustfile.py \
    --host http://localhost:8000 \
    --headless \
    --users 50 \
    --spawn-rate 5 \
    --run-time 3m \
    FullAppUser \
    --html loadtest/reports/latency.html \
    --csv loadtest/reports/latency
```

`FullAppUser` exercises common read-only endpoints including:

* Health
* Browse movies
* Search
* Show details
* User profile
* Booking history

This measures overall application latency under realistic traffic.

# Locust Options

| Option              | Description                             |
| ------------------- | --------------------------------------- |
| `--users N`       | Maximum concurrent virtual users        |
| `--spawn-rate N`  | Users started per second                |
| `--run-time T`    | Test duration (`30s`, `5m`, `1h`) |
| `--host URL`      | Target application                      |
| `SeatBookingUser` | Booking workload                        |
| `RateLimitUser`   | Rate limiter workload                   |
| `FullAppUser`     | General application latency             |
| `--tags`          | Run selected tasks                      |
| `--exclude-tags`  | Exclude tagged tasks                    |

Multiple user classes may be run together:

```bash
SeatBookingUser RateLimitUser
```

# Understanding the Results

Example statistics:

```text
Type  Name                     # reqs   # fails | Avg  Min  Max  Med | req/s
GET   GET show details           1243        0 | 14    6   180   12 | 10.2
GET   Movies                      998        0 |  9    4    95    8 |  8.1

--------------------------------------------------------------

Aggregated                       5321        0 | 11    4   180   10 | 43.7
```

## Metrics

| Metric | Meaning                  |
| ------ | ------------------------ |
| Avg    | Average response time    |
| Med    | Median (50th percentile) |
| Min    | Fastest request          |
| Max    | Slowest request          |
| req/s  | Requests per second      |

The **Aggregated** row represents overall application performance.

---

## Percentiles

```text
Name          50% 66% 75% 90% 95% 99% 100%

Aggregated    10  13  16  28  41  95  180
```

Example:

```
p95 = 41 ms
```

means:

> 95% of all requests completed within 41 milliseconds.

Percentiles are generally more useful than averages because averages can hide occasional slow requests.

# Interpreting Latency Correctly

* Locust and the application run on the same machine, so network latency is negligible. The reported times are effectively server-side latency.
* Aggregated latency depends on the task mix defined by `@task(...)` weights in `FullAppUser`.
* Use `ENV=TESTING` when measuring latency. If the rate limiter is enabled, fast `429` responses can make latency appear artificially lower.
* The first request to a show may be slower because it builds and caches the seat layout in Redis. Later requests use the cache.

---

# Notes

* Seats are finite. Once the show is sold out, booking requests will naturally return `400` or `409`. Re-run the seeder before another large booking test.
* The rate limiter is per client IP. Since all Locust traffic originates from the same machine, every virtual user shares the same token bucket.
* Keep `ENV=TESTING` for booking benchmarks to prevent throttling from affecting throughput measurements.
* `loadtest_data.json` and everything inside `loadtest/reports/` are generated artifacts and should be added to `.gitignore`.
